# docs 目录规则

本文件约束 `docs/` 下的 Wiki 和功能需求文档。新增文档应遵循本规则；已有文档可以在自然修改时逐步整理，不要求为了改目录而一次性搬迁历史内容。

## 目录总览

```text
docs/
├── AGENTS.md                 # 本目录规则
├── wiki/                     # 稳定、可复用的项目知识
│   ├── README.md             # Wiki 首页和导航
│   ├── product/              # 产品概念、用户流程、使用说明
│   ├── architecture/         # 系统架构、模块边界、关键设计
│   ├── development/          # 开发、调试、测试和本地环境
│   ├── operations/           # 部署、运行、监控和故障处理
│   └── decisions/            # 已确认的架构或技术决策
└── features/                 # 按需求组织的设计和实施资料
    └── YYYY-MM-DD-<slug>/    # 一个需求一个目录
        ├── design.md         # 简单需求的主描述
        ├── design.html       # 复杂需求的主描述，和 design.md 二选一
        └── ...               # 该需求的补充资料
```

目录分类可以随项目增长调整，但 Wiki 首页必须维护入口，避免文档只能依靠搜索发现。现有 Wiki 已按产品、架构、运行和决策主题完成归类；新增文件按上述分类放置。

## Wiki 规则

Wiki 用于记录跨需求、相对稳定、可以被多人反复查阅的知识。适合放入 Wiki 的内容包括产品使用方式、系统架构、接口协议、开发流程、部署运维、测试方法和已经确认的技术决策。

每篇 Wiki 文档应满足以下要求：

- 使用清晰的中文标题；必要时在标题下写明适用版本、状态和最后更新日期。
- 只描述当前有效的行为、约定或结论。过时内容应更新、标记为历史，或移入决策记录。
- 给出前置条件、操作步骤、输入输出和失败处理；涉及命令时提供可直接复制的示例。
- 文档之间通过相对链接互相引用，并在 `wiki/README.md` 中为主要入口提供导航。
- 一个页面聚焦一个主题。需求实现过程、临时方案和只服务于单个需求的材料放到对应的 `features` 目录。
- 需要记录取舍时，在 `wiki/decisions/` 中说明背景、选择、影响和状态；不要把未确认的讨论写成规范。

建议的 Wiki 导航分组如下：

- `product/`：用户能做什么，以及典型使用流程。
- `architecture/`：系统分层、数据流、模块接口和生命周期。
- `development/`：本地开发、代码约定、测试和排障。
- `operations/`：部署、配置、运行维护、监控和恢复。
- `decisions/`：已批准的技术决策及其后续影响。

## Features 规则

默认情况下，一个需求只能有一个 feature 目录。需求的所有设计、实施状态、验证记录和补充材料都放在这个目录内，避免同一需求的资料分散在多个位置。

### 目录命名

目录格式为：

```text
YYYY-MM-DD-<short-slug>
```

其中：

- `YYYY-MM-DD` 是需求正式创建或进入设计的日期，使用 ISO 8601 格式并放在最前面。
- `<short-slug>` 使用小写英文、数字和短横线，表达稳定且容易检索的需求名称。
- 同一天的多个需求仍然分别建立目录；名称不能只依赖序号。

例如：

```text
features/
└── 2026-11-04-agent-conversations/
```

日期表示文档目录的创建日期，不因为后续修改而改变。若需求后来拆分，应建立新的需求目录，并在两个 `design` 文档中互相链接。

### 主描述文件

每个 feature 目录必须有且只有一个主描述文件，二选一：

- `design.md`：默认选择。适用于文字、表格、代码片段和普通流程图足以表达的需求。
- `design.html`：复杂需求使用。适用于需要交互原型、复杂布局、多个状态视图或富视觉表达的设计。

`design.md` 和 `design.html` 不能同时作为主描述文件。主描述文件至少应说明目标、范围、用户场景、行为规则、数据或接口影响、验收标准、状态和日期。复杂设计仍应在 HTML 中提供可读的标题和导航，必要时在同目录补充纯文本说明。

补充文件可以使用能表达内容的明确名称，例如 `implementation-status.md`、`verification.md` 或 `api-notes.md`。补充文件不能取代主描述文件，也不能在 feature 目录外复制同一份需求说明。

### 数据库变更

如果 feature 会修改数据库表结构、索引或迁移，必须在主描述中明确列出变更，并先按仓库根目录 `AGENTS.md` 完成审核；审核通过后才能实施相关变更。

### 状态与链接

主描述中的状态至少使用以下之一：`草稿`、`设计中`、`实施中`、`已完成`、`已废弃`。完成需求后应补充验证结果，并从相关 Wiki 页面链接回 feature 目录；Wiki 只保留稳定结论，feature 目录保留需求的完整上下文。

新增或移动文档后，应同步更新所在目录的 `README.md` 或导航页，并检查相对链接。提交前至少检查目录命名、主描述文件是否存在、链接是否有效，以及文档中的状态和日期是否准确。
