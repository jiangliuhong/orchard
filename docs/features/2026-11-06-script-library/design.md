# 工作流脚本库

状态：实施中

日期：2026-11-06

## 1. 目标

当前工作流中的 `shell` 和 `code.nodejs` 节点以工作流文件内的脚本为单位。脚本无法在多个工作流之间复用，也缺少独立的编辑、版本管理和测试入口。这个 feature 增加一个可被工作流引用的脚本库，使脚本成为可独立维护、测试和发布的复用能力，并让 Agent 能够在受控范围内新增或修改脚本。

第一阶段覆盖 Node.js 和 Shell 两种脚本类型，与现有节点运行协议保持一致。脚本必须声明输入和输出 Schema；工作流引用固定脚本版本，脚本变更不会静默改变已发布工作流的行为。

## 2. 范围

### 包含

- 脚本库列表、详情、创建、编辑、复制、归档和版本查看。
- Node.js 与 Shell 脚本定义及源码保存。
- 脚本输入 Schema、输出 Schema、运行参数和说明。
- 脚本草稿、版本和发布状态。
- 在脚本详情页手动执行测试，查看输入、输出、日志、错误和耗时。
- Agent 在脚本库上下文中新增脚本、修改脚本和生成测试输入。
- 工作流节点引用脚本库中的已发布版本。
- 工作流编辑和发布时校验脚本引用、输入绑定和输出 Schema。
- 已发布工作流按不可变脚本版本运行。

### 不包含

- 任意 npm 包在线安装或脚本依赖解析。
- 让脚本获得 Agent 工具、网络访问或宿主数据库访问能力。
- 工作流运行中自动追踪最新脚本版本。
- 多工作流共享可变工作目录。
- 用户自定义运行时镜像或任意编译器安装。
- 将现有工作流内嵌脚本自动迁移为脚本库对象；后续可以提供显式导入。

## 3. 用户场景

### 3.1 创建和发布脚本

用户在脚本库中创建脚本，选择运行时 `nodejs` 或 `shell`，填写名称、说明、输入 Schema、输出 Schema 和源码。保存后形成脚本草稿；通过校验和测试后发布一个不可变版本。

脚本的名称、说明、Schema 和源码属于同一个版本快照。已发布版本只读；修改已发布脚本会创建新的草稿版本，不能覆盖原版本。

### 3.2 测试脚本

用户提供符合输入 Schema 的 JSON 输入，点击测试。系统使用和正式运行相同的运行器、超时、输出限制、环境隔离和结果解析逻辑执行脚本，并返回：

- 测试状态：成功、输入校验失败、脚本失败、超时、输出超限或系统错误。
- 结构化输出及输出 Schema 校验结果。
- stdout、stderr、退出码和耗时。
- 被测试的脚本版本号。

测试使用脚本当前草稿快照，允许用户在发布前验证修改。测试不会创建工作流版本，不会改变脚本发布版本，也不会修改脚本源码。

### 3.3 Agent 修改脚本

用户在脚本详情页向 Agent 描述需求。Agent 获得当前脚本、Schema、说明、最近测试结果和必要的项目规则，在脚本工作区中提出文件变更。用户确认后，变更应用到脚本草稿并触发语法、Schema 和引用检查。

Agent 可以：

- 新建脚本草稿。
- 修改当前脚本源码、说明、输入 Schema 和输出 Schema。
- 根据失败的测试结果提出修复。
- 生成或调整测试输入。

Agent 不可以直接发布脚本、修改已发布版本、改变工作流引用或执行未确认的文件变更。Agent 输出必须经过宿主的文件路径、大小、Schema 和脚本定义校验。

### 3.4 工作流引用脚本

工作流新增一种脚本引用配置，节点仍然使用现有输入绑定和输出 Schema 机制。例如：

```json
{
  "id": "normalize",
  "name": "Normalize text",
  "type": "script",
  "input": {
    "source": "object",
    "properties": {
      "text": { "source": "workflow", "pointer": "/text" }
    }
  },
  "config": {
    "scriptId": "script-normalize-text",
    "scriptVersionId": "script-version-3"
  }
}
```

编辑器默认选择脚本的当前可用发布版本，但保存工作流定义时必须写入明确的 `scriptVersionId`。工作流发布时再次确认该版本存在且可用。已发布工作流永远使用保存的版本快照；脚本库发布新版本不会改变既有工作流。

脚本版本的输入 Schema 用于工作流编辑和运行前校验。节点可以声明更严格的输入或输出 Schema，但不能放宽脚本版本的契约。节点输出必须同时满足脚本输出 Schema 和节点输出 Schema。

## 4. 脚本协议

### 4.1 通用定义

脚本版本至少包含：

| 字段 | 说明 |
| --- | --- |
| `id` | 脚本稳定 ID |
| `versionId` | 不可变版本 ID |
| `runtime` | `nodejs` 或 `shell` |
| `entryFile` | 版本源码中的入口文件 |
| `inputSchema` | 严格 JSON Schema |
| `outputSchema` | 严格 JSON Schema |
| `timeoutMs` | 受允许范围限制的超时 |
| `source` | 脚本源码文件集合 |
| `description` | 面向用户和 Agent 的用途说明 |

脚本只能读取宿主通过 stdin 或约定环境变量提供的 JSON 输入，不能把输入拼进命令行。输出必须通过现有运行协议生成结构化 JSON；日志和业务输出分开处理。脚本测试和工作流运行共用同一执行入口。

### 4.2 Node.js

Node.js 脚本沿用现有默认导出函数协议：

```ts
export default async function run(input: { text: string }) {
  return { normalized: input.text.trim() };
}
```

允许 Node 内置模块；第一阶段不允许从脚本源码动态安装或加载 npm 依赖。相对文件引用必须指向同一脚本版本中的合法源码文件。TypeScript 编译、入口检查和输出序列化由宿主完成。

### 4.3 Shell

Shell 脚本沿用现有 Shell 节点协议：stdin 接收 JSON 字符串，脚本通过 `$ORCHARD_RESULT_FILE` 写入结构化结果。使用固定 Shell 执行器和受控环境，不把用户输入拼接为命令。

Shell 脚本的入口文件必须是版本源码中的一个文件。默认使用 `/bin/bash`，脚本退出码非零时测试和工作流节点均失败，即使结果文件已经存在。

### 4.4 运行限制

脚本库复用现有运行限制，具体上限以运行器配置为准：

- 每次测试和每次节点执行使用独立临时目录。
- 设置默认超时和最大允许超时。
- 限制 stdout、stderr 和结构化结果大小。
- 超时或取消时终止完整进程组。
- 不继承用户工作流目录中的文件。
- 不允许绝对路径、`..`、符号链接和非法扩展名。
- 测试和正式运行均不自动重试脚本。

## 5. 生命周期和版本规则

脚本状态建议为：`draft`、`published`、`archived`。

- 新建脚本首先拥有一个草稿版本。
- 草稿可以编辑和测试；同一脚本最多一个可编辑草稿版本。
- 发布前必须通过源码、Schema、入口文件和引用完整性校验。
- 发布后版本不可变，并记录源码与 Schema 摘要。
- 编辑已发布脚本时创建新的草稿版本，原发布版本继续可被工作流使用。
- 归档脚本禁止新工作流引用，但不影响已经绑定该版本的已发布工作流运行。
- 如果草稿发布时存在使用旧版本的工作流，不自动升级这些工作流。
- 删除采用归档或逻辑删除，保留被工作流版本和测试记录引用的版本。

脚本库的草稿修订需要使用期望修订号和幂等请求 ID，避免 Agent 会话、编辑页面和测试请求互相覆盖。测试请求必须携带脚本草稿修订号；如果测试期间草稿发生变化，服务端拒绝将结果标记为当前草稿的测试结果。

## 6. Agent 集成

### 6.1 上下文

脚本 Agent 继续使用现有 Agent Provider 和对话机制，但上下文对象从工作流草稿改为脚本草稿。每次请求至少包含：

- 脚本元数据和当前修订号。
- 当前源码文件和入口文件。
- 输入、输出 Schema 及校验错误。
- 最近一次或用户选定的测试结果。
- Agent 可用操作和脚本运行限制。

上下文中不包含密钥、其他脚本的私有源码、其他工作流的未授权内容或任意宿主文件。

### 6.2 变更协议

Agent 返回结构化结果，变更操作限定为：

- `create`：创建脚本文件或脚本草稿。
- `update`：替换已有脚本文件或元数据字段。
- `delete`：删除草稿中的未引用源码文件。
- `test-input`：生成一个用于测试的 JSON 输入。

宿主逐项校验操作，拒绝越界路径、重复文件、非法运行时、非法 Schema、超出大小限制或删除入口文件的结果。用户确认后以一个修订原子应用所有操作；应用后自动执行静态校验，不自动发布。

### 6.3 对话状态

脚本 Agent 对话应绑定脚本草稿，不绑定已发布脚本版本。脚本草稿删除或归档时，相关对话只读保留。脚本 Agent 的多轮会话复用现有 Agent 对话能力，但不允许通过 Agent 直接修改工作流文件。

## 7. API 草案

具体命名以现有 API 风格为准，以下接口用于确定能力边界：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/scripts` | 分页查询脚本库，支持 runtime、状态和关键词过滤 |
| `POST` | `/scripts` | 创建脚本和初始草稿 |
| `GET` | `/scripts/:id` | 查询脚本详情、当前草稿和发布版本 |
| `PATCH` | `/scripts/:id/draft` | 按修订号更新脚本草稿 |
| `POST` | `/scripts/:id/versions` | 校验并发布当前草稿 |
| `GET` | `/scripts/:id/versions/:versionId` | 查询不可变脚本版本 |
| `POST` | `/scripts/:id/tests` | 测试指定草稿或脚本版本 |
| `GET` | `/scripts/:id/tests/:testId` | 查询测试结果和日志 |
| `POST` | `/scripts/:id/agent/turns` | 提交 Agent 请求 |
| `POST` | `/scripts/:id/agent/apply` | 确认并应用 Agent 变更 |
| `POST` | `/scripts/:id/archive` | 归档脚本 |

测试 API 返回受控的结构化结果和诊断信息，不返回宿主临时目录、环境变量、绝对路径或内部凭据。

## 8. 工作流格式影响

现有 `code.nodejs` 和 `shell` 节点继续支持工作流内嵌脚本。新增 `script` 节点或在现有节点配置中增加脚本库引用时，需要明确区分以下两种来源：

- `source: "inline"`：现有工作流内脚本，保持兼容。
- `source: "library"`：脚本库版本引用，必须包含 `scriptId` 和 `scriptVersionId`。

本设计建议新增 `script` 节点，避免同一节点同时承载本地文件路径和脚本库 ID，减少发布与运行时分支。最终格式示例：

```json
{
  "type": "script",
  "input": { "source": "workflow" },
  "config": {
    "scriptId": "normalize-text",
    "scriptVersionId": "normalize-text-v3"
  },
  "outputSchema": {
    "type": "object",
    "required": ["normalized"],
    "properties": { "normalized": { "type": "string" } }
  }
}
```

格式版本是否从 `1` 升级，需要在实现阶段根据现有解析器的兼容策略决定；如果新增节点类型可被旧解析器明确拒绝，应升级格式版本并补充迁移提示。旧工作流的内嵌脚本行为保持不变。

## 9. 数据持久化方案（需审核）

该 feature 预计需要新增数据库表或等价持久化结构，具体 DDL 和迁移必须先按仓库根目录 `AGENTS.md` 完成审核，审核通过后才可实施。当前文档只记录逻辑模型，不执行数据库变更。

建议的逻辑实体：

| 实体 | 主要字段 | 作用 |
| --- | --- | --- |
| `scripts` | `id`、名称、描述、运行时、状态、当前草稿版本、当前发布版本、时间戳 | 脚本稳定身份和生命周期 |
| `script_versions` | `id`、`script_id`、修订号、源码快照、Schema、入口文件、摘要、状态、创建者、时间戳 | 不可变脚本版本和草稿快照 |
| `script_tests` | `id`、脚本版本或草稿修订、输入、结果、状态、日志、耗时、时间戳 | 测试历史和诊断 |
| 工作流版本引用 | `script_id`、`script_version_id` 或定义 JSON 中的等价绑定 | 固化工作流使用的脚本版本 |

需要重点审核：脚本源码和测试输入输出的存储上限、日志保留策略、版本删除约束、脚本版本与工作流版本的外键关系、草稿并发约束、历史数据迁移及备份回退方案。若现有文件存储适合保存源码，应由数据库只保存受校验的内容引用和摘要，不能让前端提供任意文件路径。

## 10. 页面和交互

第一阶段页面至少包含：

1. 脚本库列表：名称、运行时、状态、当前发布版本、最近更新时间和测试状态。
2. 脚本编辑页：源码编辑器、入口文件、输入 Schema、输出 Schema、说明、运行参数和版本状态。
3. 测试面板：JSON 输入编辑、运行按钮、输出、日志、Schema 校验结果、耗时和版本标识。
4. 版本页：草稿与已发布版本差异、发布操作、历史版本查看和回滚式复制为新草稿。
5. Agent 面板：对话、变更预览、测试结果引用、应用变更和重新测试。
6. 工作流节点配置：搜索脚本、选择发布版本、显示输入输出 Schema，并提示脚本新版本可用但不会自动升级。

发布、归档和应用 Agent 变更都应显示当前修订号和影响范围。脚本测试失败时保留可复制的输入和错误信息，便于 Agent 继续修复。

## 11. 验收标准

### 脚本库

- 用户可以创建 Node.js 和 Shell 脚本，保存输入 Schema、输出 Schema、源码和说明。
- 非法入口、非法文件路径、非法 Schema、超限源码和不支持的运行时会被拒绝。
- 已发布版本不可修改；修改操作只能创建新的草稿版本。
- 归档脚本不能被新工作流引用，既有已发布工作流仍可运行。

### 测试

- 有效输入可以使用与正式运行相同的运行协议执行并返回结构化输出。
- 输入不符合输入 Schema 时不会启动脚本。
- 输出不符合输出 Schema、非零退出、超时、取消和输出超限均有明确失败状态。
- 测试结果绑定到执行时的脚本草稿修订或不可变版本，不能伪装成更新草稿的结果。
- 测试不会发布脚本、改变工作流版本或覆盖源码。

### Agent

- Agent 可以根据脚本上下文新增或修改源码及 Schema，并能引用测试失败结果。
- Agent 不能直接发布、修改已发布版本或访问未授权脚本和宿主文件。
- 用户确认前变更只以预览形式存在；确认后以单次修订原子应用。
- Agent 变更应用后自动校验，校验失败时保留可修复草稿并显示具体错误。

### 工作流

- 工作流可以选择并引用已发布脚本版本，保存后定义包含明确版本 ID。
- 工作流编辑和发布会校验脚本版本存在、未被禁止使用且输入输出契约兼容。
- 工作流运行使用绑定的不可变脚本版本；脚本库新发布版本不影响已发布工作流。
- 现有内嵌 `shell` 和 `code.nodejs` 工作流行为及旧版本工作流继续可用。

### 安全与运行

- 脚本测试和工作流执行使用统一超时、输出上限、进程组终止和临时目录隔离。
- API 和日志不会泄露绝对路径、环境变量、凭据或其他脚本源码。
- 并发编辑、测试和 Agent 应用之间的修订冲突可检测并返回明确错误。

## 12. 实施拆分建议

1. 确认脚本库领域模型、源码存储方式、版本语义和数据库迁移方案；完成数据库结构审核。
2. 提取现有 Node.js/Shell 执行器的共享运行接口，确保脚本测试和工作流节点使用同一安全边界。
3. 实现脚本库 CRUD、草稿修订、版本发布和归档 API。
4. 实现脚本测试 API、结果存储和测试面板。
5. 扩展工作流格式、校验器、编辑器和运行器，支持固定脚本版本引用。
6. 接入脚本 Agent 上下文、变更协议、预览和原子应用。
7. 补充权限边界、并发冲突、版本兼容、失败运行和回归测试。
8. 更新工作流格式 Wiki、API Wiki 和本 feature 的实施状态与验证记录。

## 13. 风险和待确认事项

- **节点格式**：采用独立 `script` 节点，还是在 `code.nodejs` / `shell` 中增加 library source，需要在实现前确定；本文推荐独立节点。
- **源码存储**：需要决定源码放数据库还是现有文件存储；两者都必须支持不可变快照和完整性摘要。
- **权限模型**：当前项目的用户和资源权限边界需要确认，脚本库是否按用户、工作区或全局共享需要产品决策。
- **依赖管理**：第一阶段不支持 npm 安装；若未来支持，需要单独设计依赖锁定、缓存、网络隔离和供应链审核。
- **数据库结构**：任何表、字段、索引、外键或迁移执行前，都必须获得仓库规则要求的审核。
- **版本升级体验**：工作流是否提供“升级到脚本最新版本并生成新草稿”的辅助操作，建议作为后续能力，不在首次实现中自动升级。
