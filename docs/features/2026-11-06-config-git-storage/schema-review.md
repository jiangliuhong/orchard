# 配置 Git 存储数据库审核方案

状态：审核通过（2026-11-06）  
关联设计：[design.md](design.md)  
审核结论：用户在本次会话明确回复“确认”，批准本方案并进入全部编码及后续真实验证。

## 1. 审核范围与前置条件

用户要求的执行顺序为：数据库审核通过 → 完成全部编码和自动化检查 → 真实验证。本次审核既覆盖数据库结构影响，也覆盖现有业务表的导入语义和跨存储恢复协议；在审核通过前不开始本功能编码。

本方案不新增或修改表、字段、索引、触发器，不增加迁移，不提升数据库版本。保持现有不可变版本和唯一约束，新增能力通过领域导入接口、现有事务/回执和 data-dir 下文件实现。不得通过移除触发器、关闭外键或导入 SQL 文件绕过约束。

只读依据：`src/persistence/store.ts` 的 transaction/command，`src/persistence/schema.ts` 的版本唯一性及不可变触发器，`src/authoring/service.ts` 的发布逻辑，`src/persistence/files.ts` 的内容寻址产物，以及 `src/server/app.ts` 的初始化顺序。设计并不声称已有完整导入接口或统一写入协调器。

## 2. 表写入矩阵

| 现有表 | 允许的变化 | 不变量 |
| --- | --- | --- |
| workflows | 新对象插入；同 ID 更新名称、current_version_id、updated_at | 保留 created_at 与目标独有对象；指针只能指向本对象版本 |
| workflow_versions | 缺失发布版本按固定 ID 插入 | 已存在行不得 UPDATE/DELETE；同 ID 不同定义或归属拒绝 |
| drafts | 创建未发布/编辑草稿；更新已有草稿的源码路径、校验、基线及修订 | 不导入源本机 revision；已有修订仅在内容改变时递增；不复用已发布草稿作为编辑草稿 |
| scripts | 插入对象；更新名称、说明、归档状态、草稿/发布指针及时间 | runtime 不允许在同 ID 下改变；目标独有对象保留 |
| script_versions | 插入缺失发布版本或本机草稿；更新目标现有 draft 内容及修订 | published 行不可修改；每脚本至多一个 draft；version_no 在对象内唯一 |
| provider_settings | 新适配器设置插入或已有设置更新 | 必须有已注册适配器；内容改变才递增 revision；保留本机 executable 映射及外部认证 |
| command_receipts | 插入 config-git:restore scope 的事务回执 | 与上述业务写入同一事务；相同 requestId 不同计划拒绝；禁止作为文件阶段完成证明 |
| artifacts | 若复用的持久化接口确需登记产物，可新增内容寻址记录 | 不覆盖已有不同摘要记录，不清理恢复点需要的内容 |
| runs、node_runs、node_attempts、script_tests、authoring_turns、对话/事件记录 | 不从快照导入、不回退、不伪造测试成功 | 历史引用及执行记录保持不变；维护窗口内不接受新执行 |

文件写入包括 Bridge 配置、常规快照/偏好交付、本机映射、操作日志、暂存文件、恢复点及源码产物。Git 绑定和认证不随配置恢复改变。

## 3. 身份、序号、草稿与指针

- 发布版本稳定 ID 是跨设备身份；数据库 version_no 为本机显示顺序，不导出。事务内针对每个对象按 MAX(version_no)+1 分配新序号，同批按版本 ID 排序；已有版本保持序号。
- 同 ID 已存在时比较归属与可移植定义摘要；摘要不使用包含编译产物的数据库 content_hash。相同则复用，不同则在任何业务写入前拒绝。
- 目标草稿本机行 ID 与 revision 不属于发布版本身份；快照 draft 表示可编辑内容。已有目标草稿更新原行并递增修订，新目标草稿生成本机 ID。脚本版本定义中的 versionId 仅发布版本必需，草稿使用 null；发布后才将本机草稿 ID 固化为发布版本 ID。
- 导入发布版本 ID 恰好占用目标草稿 ID 时拒绝，不自动把目标草稿发布或迁移其身份。
- workflow 未发布草稿可没有 workflows 行；通过 workflow.json 中稳定 ID 匹配。一个稳定 ID 多个候选草稿时报告冲突。新增未发布草稿保留 workflow_id=null；若计划有发布版本，则先建立 workflow 与版本再关联草稿。
- 工作流草稿 baseVersionId 纳入版本闭包，导入后仍必须属于该工作流。基线早于当前发布指针的草稿允许保留，但预览提示其后续发布可能触发现有 BASELINE_CONFLICT，恢复不伪造基线。
- 已有对象的源发布指针为 null 时保留目标指针；源草稿为空时保留目标草稿；实际覆盖必须预览。新增对象可以没有发布版本和草稿，但须满足领域状态约束；无法满足则拒绝快照。
- archived 脚本可以作为固定依赖导入，但不开放新的引用。归档对象可保留不可变版本与草稿，普通发布限制不被绕过。
- 普通发布方法会生成 ID、冻结模型或检查编辑基线，因此新增专用导入方法；抽取静态校验而不是调用现有发布命令。Provider 隐藏模型通过完整模型目录导入，不使用过滤后的视图。

## 4. 单事务顺序

异步编译、Schema/依赖校验、文件读写准备均在事务前完成。获得配置排他窗口后再次校验活动数和预览目标摘要，固定最终计划。

1. 将全部新源码产物写入内容寻址路径并持久化；保存完整恢复点、待安装文件及 prepared 日志。
2. 调用 Store.command("config-git:restore", requestId, finalPlan, action)。已有回执先核对请求摘要，不重复业务写入。
3. 事务内先创建缺失对象行（允许的指针先为 null），插入脚本发布版本和草稿，再插入工作流发布版本及草稿；Provider 定义更新与其余业务更新在同一事务内完成。
4. 最后更新对象指针与状态，检查版本归属、唯一序号、脚本契约、草稿基线和计划后定义完整性。原有运行、对话和测试记录不变。
5. 在同一事务插入回执，result_json 保存 operationId、planHash、recoveryPointId 及数据库阶段结果。事务失败时业务行与回执一起回滚。
6. 提交后安装可变配置文件、重载缓存并验证最终摘要，持久化 completed 后才允许 API 报告恢复成功。

Store.transaction 是同步接口，不能把 Promise、Git 调用或异步文件校验放进其回调。业务事件不得在文件完成前向客户端暴露混合状态，恢复窗口内屏蔽相关业务读写，最终统一刷新。

## 5. 故障恢复与数据保留

数据库提交与文件日志更新之间存在不可避免的中断窗口，因此启动必须以事务回执判断提交事实：

| 日志/回执状态 | 动作 |
| --- | --- |
| prepared 且无匹配回执 | 数据库保持旧状态；清理或隔离本操作暂存内容；已有配置文件未被替换 |
| prepared 或后续阶段，存在匹配回执 | 数据库已提交，使用持久化计划补齐文件新状态；不重跑业务写入 |
| 回执计划摘要不符、文件缺失/损坏、安装失败 | recovery_required，保持维护状态，保留全部证据与恢复点 |
| completed | 校验必要持久化状态后正常初始化缓存及运行队列 |

启动恢复必须先于 Store.recoverBusiness、服务缓存初始化及队列 start。使用独立 config-git/staging，避免现有 recoverBusiness 清理普通 staging 时删除恢复材料。

提交后只做向前补齐；需要回到旧配置时，在完成或修复一致状态后，用恢复点创建新的预览/恢复操作。不得拷贝旧数据库覆盖当前数据库，也不得删除新发布版本来撤销恢复。恢复点包含必要产物的独立副本，不能依赖垃圾回收可能删除的外部路径。

所有定义写入、异步活动、队列启动、Bridge 调用及清理须接入同一协调器；有 queued/running/cancel_requested 等活动时拒绝恢复。排他获取和活动检查不可分离。跨进程继续使用 data-dir DirectoryLease。
