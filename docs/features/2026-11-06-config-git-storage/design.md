## 1. 目标

将 Orchard 的设置、工作流定义和脚本定义导出为可阅读、可编辑、可比较差异的脚本文件，存入用户指定的 Git 仓库。用户可以手动提交当前配置，也可以选择仓库中的历史提交恢复配置，用于配置备份、跨设备迁移和版本回退。

Git 保存定义快照；Orchard 继续使用现有存储运行。普通编辑和保存不触发 Git 提交、推送或恢复。本文保留已审核设计，实际实现与验证结果分别见 [implementation.md](implementation.md) 和 [verification.md](verification.md)。

## 2. 范围

| 对象 | 纳入 Git 的内容 | 不纳入的内容 |
| --- | --- | --- |
| 常规设置 | 当前外观模式（浅色、深色、跟随系统），以后通过明确 Schema 扩展的偏好 | 浏览器缓存、临时界面状态 |
| Provider | 稳定 ID、启用状态、非敏感连接配置、transport、默认模型、模型目录及启停/隐藏状态 | 登录凭据、auth.json、CLI 用户配置原文、运行中会话、检测/验证结果 |
| Web Bridge | 应用定义、环境 ID 与 origin、启用状态、用户配置的工具定义与工具开关；环境中的 profileId/extensionId 按本机绑定处理 | Cookie、Token、标签页绑定、bound/tabAvailable、连接状态、Native Host 安装文件 |
| 工作流 | 稳定 ID、名称、定义、布局、内嵌脚本、当前草稿、当前发布版本，以及依赖闭包要求的定义 | Run、节点尝试、日志、输入输出、Agent 对话、测试历史 |
| 脚本库 | 稳定 ID、名称、说明、运行时、入口、输入输出 Schema、超时、Shell 输出协议、源码、草稿、当前发布版本及被工作流引用的发布版本 | 执行产物、测试记录、Agent 对话、可重新生成的编译产物 |

首期每次提交导出以上所有类别，恢复可按类别选择；选择工作流时必须纳入缺失的脚本依赖，或确认目标已有相同版本与摘要。首期不支持后台同步、定时提交、自动合并、自动解决 Git 冲突或将 Git 用作运行数据库。

Git 历史承担导出之后的配置历史，不把应用中所有旧版本全量搬进首个提交。仍被所选工作流引用的旧脚本版本必须导出，即使脚本已归档。

## 3. 当前实现与设计依据

- 设置页当前有常规、Provider、Web Bridge 三个分类，见 `src/web/features/SettingsPage.tsx`。外观为浏览器偏好；导出不能假定服务端已有该值。
- Provider 保存于现有 `provider_settings`，模型状态和配置修订必须保留其业务含义；认证仍由本机 CLI 管理，见 [Provider 说明](../../wiki/architecture/providers.md)。
- Web Bridge 当前由 `src/web-bridge/config.ts` 管理 `config/web-bridge.json`，包含应用、环境、自定义工具和开关。导出按当前实现覆盖工具定义，并剔除连接状态。
- 工作流和脚本版本不可变；工作流使用固定 `scriptId` / `scriptVersionId`，见 [流程格式](../../wiki/architecture/workflow-format.md)和[脚本库设计](../2026-11-06-script-library/design.md)。

## 4. 仓库与脚本格式

### 4.1 远端仓库绑定（已确认方案）

首期以远端绑定为接入入口，支持 GitHub、GitLab 和自建 Git 服务的已有仓库；用户在对应平台创建远端仓库，Orchard 不调用平台 API 创建仓库。一个 data-dir 绑定一个远端、一个固定分支和一个配置目录。

设置页新增“Git 配置存储”，表单如下：

| 字段 | 规则 |
| --- | --- |
| 仓库地址 | 支持 SSH（如 `git@github.com:team/config.git`）和 HTTPS；禁止内嵌密码或 Token |
| 分支 | 检测连接后列出远程分支供选择；空仓库默认填写 `main`，首次推送时创建 |
| 配置目录 | 默认 `orchard-config/`，绑定时可修改，必须是仓库内的合法相对路径 |
| 认证方式 | 复用运行 Orchard 的操作系统用户的 SSH agent/key 或 Git credential helper |
| 提交身份 | 优先读取本机 Git name/email；缺失时要求填写，仅保存到当前副本的 Git 配置 |

Orchard 在 `<data-dir>/config-git/repositories/<binding-id>/` 创建专用本地副本，用户无需选择本地目录。首期不提供任意已有本地工作目录的绑定入口；绑定后的专用副本支持仅本地提交和读取本地历史。

接入步骤：填写地址 → 检测连接 → 选择分支和配置目录 → 创建专用副本并检查内容 → 保存绑定 → 用户选择首次提交或恢复。

“检测连接”使用 `git ls-remote` 验证读取权限并获取分支，不创建测试提交。读取成功只显示“连接成功，推送权限尚未验证”。Git 子进程关闭交互提示并设置超时；认证失败返回指引。SSH 未知主机要求用户先在运行 Orchard 的机器上验证主机密钥，不自动接受未知密钥。

| 仓库状态 | 绑定后的引导 |
| --- | --- |
| 空仓库 | 提示“提交当前配置”，首次推送创建目标分支 |
| 已有内容但配置目录不存在 | 提示将当前配置添加到仓库，保留其他文件 |
| 配置目录包含有效快照 | 提供“预览并恢复仓库配置”和“预览并提交当前配置” |
| 配置目录非空但格式无效 | 阻止覆盖，要求换目录或修复文件 |
| 快照格式高于当前版本 | 保留绑定，提示升级后才能恢复，不允许用当前格式覆盖 |

绑定成功前的副本属于暂存状态，克隆或检查失败不留下有效绑定；重试不能覆盖已有副本。绑定不导入、不提交、不推送配置。

绑定信息保存在 data-dir 的独立本地文件，不随配置快照导出，避免恢复历史配置时切换仓库。界面不保存仓库密码或 Token。解除绑定保留应用配置、本地副本、未推送提交和恢复资料；重新绑定使用新的 binding ID。解除绑定与其他 Git 写操作互斥。

### 4.2 文件组织

```text
orchard-config/
  manifest.json
  settings/
    general.config.ts
    providers/<provider-id>.config.ts
    web-bridge.config.ts
  workflows/<workflow-id>/
    workflow.config.ts
    draft/
      workflow.json
      layout.json
      scripts/...
    versions/<version-id>/...
  scripts/<script-id>/
    script.config.ts
    draft/
      definition.config.ts
      src/...
    versions/<version-id>/
      definition.config.ts
      src/...
```

`manifest.json` 包含 `formatVersion`、最低兼容 Orchard 版本、导出类别、对象索引、文件列表和内容摘要。ID 必须编码为安全且无碰撞的目录名，拒绝路径穿越、符号链接、子模块和管理目录外的引用。源文件名沿用现有源码路径规则。

工作流和脚本的顶层配置声明稳定 ID、名称、归档状态、草稿路径、当前发布版本和版本清单；各版本保存完整定义与源码。目录中的原始 JSON 和源码保留现有格式，配置脚本负责组织它们。

示例 `settings/providers/pi-cli.config.ts`：

```ts
export default {
  id: "pi-cli",
  enabled: true,
  config: {
    executable: { localRef: "providers.pi-cli.executable" },
    transport: "legacy",
  },
  defaultModel: "model-id",
  models: [{ id: "model-id", name: "模型名称", source: "configured", enabled: true, deleted: false }],
};
```

示例 `scripts/normalize/versions/v1/definition.config.ts`：

```ts
export default {
  id: "normalize",
  versionId: "v1",
  name: "文本规范化",
  description: "清理文本输入",
  runtime: "nodejs",
  entryFile: "src/index.ts",
  inputSchema: {
    type: "object",
    required: ["text"],
    properties: { text: { type: "string" } },
    additionalProperties: false,
  },
  outputSchema: { type: "string" },
  timeoutMs: 10000,
  resultMode: "json",
  sourceFiles: ["src/index.ts"],
};
```

### 4.3 脚本语义

“脚本方式”首期定义为声明式 TypeScript：允许 `export default` 加 JSON 兼容字面量、注释和尾逗号。通过 AST 静态解析，禁止 import、函数调用、表达式、模板插值、展开、getter 和任何执行语句；重复属性同样拒绝。`localRef` 是受校验的数据标记。

恢复不使用 `eval`、动态 import 或执行仓库内安装脚本，也不执行工作流/脚本源码。业务源码仅保存并按现有静态规则验证，运行仍由用户另行触发。

用户可以在 Git 中编辑配置并提交；拟提供 `orchard config-git validate --refresh-manifest`，校验后重新生成索引和摘要。恢复时摘要不一致必须报错，不能悄悄重写仓库来接受修改。摘要用于完整性检查，不作为仓库来源可信的证明。

生成文件统一 UTF-8、LF 和稳定排序；数组中有业务顺序的内容保持原顺序。manifest 不包含每次变化的导出时间或本机修订号，相同配置重复导出无差异。版本 ID、对象身份和业务引用必须保留。

### 4.4 凭据和本机参数

Provider 导出使用适配器声明的字段白名单；未知敏感性字段必须阻止导出并列出字段名，不在错误信息中回显值。密钥仅保存引用，外部 CLI 认证文件始终不导出。

CLI 绝对路径、Web Bridge profileId/extensionId 等本机值默认导出为 `localRef`。恢复时优先沿用同对象的本机绑定，缺失则要求用户在预览中补充映射；不把占位符写进有效配置。需要凭据或路径的对象没有完成映射时不能应用该对象。

用户自写源码、提示词和 URL 也可能含敏感内容，提交预览必须可查看全部文件差异；不能声称字段过滤能识别源码中的所有秘密。

### 4.5 v1 数据契约

以下是首期实现必须遵守的格式约束；实现时提供对应严格 Schema（未知字段拒绝），不能仅凭示例推断导出字段。业务源码、提示词、JSON Schema 内的用户字段不受配置对象字段白名单限制。

| 文件/对象 | 必需字段及语义 |
| --- | --- |
| `manifest.json` | `formatVersion: 1`、`minOrchardVersion`（语义版本）、`categories`、`objects`、`files`。`files` 每项为相对路径、UTF-8 字节数及 SHA-256；不列 manifest 自身，防止自引用。`objects` 每项为类别、稳定 ID、入口路径、定义摘要、版本摘要清单及固定版本依赖。首期导出五类全部声明，类别缺失不等同于空类别 |
| `general.config.ts` | `theme: light/dark/system`；不包含浏览器 ID、客户端修订和待消费恢复记录 |
| Provider | `id/enabled/config/defaultModel/models`；当前 `pi-cli`、`codex-cli` 的 config 仅允许 `executable` 引用及 `transport`。缺失 transport 规范化为 legacy。模型包含 `id/name/source/enabled/deleted`，缺省布尔值规范化为 true/false，必须导出隐藏项。`source` 只允许 configured/discovered；revision、updatedAt、readiness 不导出 |
| Web Bridge | `applications/environments/tools/enabledTools`；应用包含 id/name/enabled；环境包含 id/origin/enabled 和可选 profileId/extensionId 引用；工具按现有 `WebBridgeTool` 定义导出并按业务 Schema 校验。bound/tabAvailable 不导出。工具关闭状态与自定义工具定义均须保留 |
| 工作流入口 | `id/name/currentPublishedVersionId/draft/versions`；指针及 draft 可为 null。draft 包含路径及可空 `baseVersionId`；versions 为版本 ID、路径清单；派生版本摘要仅保存于 manifest 的对象版本索引。每个版本保存 workflow.json、layout.json 及源脚本。现有工作流没有归档字段，v1 不虚构该字段 |
| 脚本入口 | `id/name/description/runtime/archived/currentPublishedVersionId/draft/versions`；draft 包含路径；草稿行 ID 为本机身份，不导出；versions 列出发布版本 ID、路径，派生摘要由 manifest 管理 |
| 脚本版本定义 | `id/versionId/name/description/runtime/entryFile/inputSchema/outputSchema/timeoutMs/resultMode/sourceFiles`；发布版本 versionId 为稳定 ID，草稿为 null；源码路径相对于所在 draft 或版本目录，必须唯一；name/description 保存该版本快照，不用对象当前名称替换历史元数据 |

工作流尚未发布时，也从草稿中的 workflow.json 提取稳定 workflow ID 并导出；数据库 `draft.workflow_id` 为 null 不代表忽略该草稿。若多个草稿声明同一 workflow ID，阻止导出并定位这些草稿，不任意选择其一。不可解析工作流身份的草稿阻止该次全量导出并提示修复；可识别身份但业务校验不通过的草稿允许导出并保留原文。

版本闭包包括当前发布版本、工作流草稿基线版本，以及这些定义引用的固定脚本发布版本。基线版本必须导出，避免恢复后草稿无法继续发布。新建对象且快照没有发布版本时，指针为 null；已有对象的源指针为 null 时保留目标发布指针，预览显示该保留规则。源 draft 为 null 时保留目标已有草稿，避免隐式删除；有源草稿时预览明确覆盖并递增本机修订。目标独有对象及历史版本始终保留。

发布版本 ID 与对象 ID 均为身份字段，数据库草稿行 ID、版本序号、修订号、时间戳和产物路径不进入可移植格式。已有目标草稿复用本机行 ID，内容变化时递增修订；新目标草稿生成本机 ID，脚本发布时才将该 ID 固化为发布版本身份。目录名使用 ID 的 UTF-8 字节的小写十六进制编码，不进行大小写折叠或截断；解码后必须等于声明 ID，超过文件系统单段限制时拒绝并定位 ID。路径始终用 `/`，禁止绝对路径、空段、`.`、`..`、`.git`、符号链接和子模块；管理目录的祖先也须检查。

定义摘要为 SHA-256，基于规范化 JSON：对象键按 Unicode 码点序排序、无空白、数组业务顺序保留、仅允许有限数字及 JSON 值。无业务顺序的对象/版本/模型/文件清单按稳定 ID 或路径排序。发布版本摘要包含稳定身份、完整定义、布局和源码文件映射，排除编译产物、版本序号、时间戳与验证结果；不直接复用包含编译产物的数据库 content_hash。目标已有版本按同一算法重新计算。文件摘要按实际字节计算，文件内容统一 UTF-8、LF；源码按此规范化后参与定义摘要。manifest 中文件集合必须与管理目录实际文件集合相等，额外文件、重复路径、重复身份均拒绝。

`--refresh-manifest` 只能在管理副本的绑定目录或 CLI 显式指定的目录运行，先解析全部声明、验证闭包和路径，再原子替换 manifest；不修改业务源码、不创建提交。更新已有发布版本内容但沿用版本 ID 不能绕过不可变性冲突；新增发布版本应使用新 ID 并同步引用。命令失败保留原 manifest。

### 4.6 本机映射与合并边界

`localRef` 只能出现在 Schema 指定的位置，形状必须为仅含一个非空字符串键值的 `{ localRef: "..." }`。Provider executable 是必需引用，Bridge profileId/extensionId 为可选引用；引用键由对象类型、稳定 ID 和字段组成，使用可逆编码防止带点 ID 碰撞。快照中声明了引用但目标没有对应本机值时，必须补齐映射才能恢复该对象；未声明可选引用时保留目标同字段，新增对象保持未绑定。登录凭据由外部 CLI 管理，不伪造或写入引用值，恢复不要求已登录。

现有 Provider 适配器须增加显式导出字段策略；未知适配器或未分类字段阻止相关导出/恢复。不能把 CLI 配置、环境变量或 adapter 的任意返回字段透传到快照。恢复后保留目标独有 Provider/模型、Bridge 应用/环境/工具；同 ID 项按快照覆盖可移植字段及明确的 enabled/deleted 标志。Provider 的隐藏模型通过专用导入接口恢复，不能使用会过滤隐藏模型的页面视图或普通更新接口。默认模型必须与合并后目录状态一致，否则预览报错。

恢复计划在依赖补齐及映射完成后重新生成，记录最终类别与对象集合；用户须确认扩展后的范围。对不合法但可保存的草稿，已有明确引用仍检查闭包；其他业务错误记录为待修复。严格发布校验使用导入后计划中的 Provider/工具/脚本定义，不以当前在线状态为准，不触发模型请求或浏览器工具调用。

## 5. 用户流程

### 5.1 手动提交到 Git

1. 主按钮为“提交并推送”，同时提供“仅本地提交”。提交并推送先 fetch 检查远端；本地没有待推送提交时允许快进到远端，再生成当前应用的一致性快照，展示相对最新远端的差异。本地已有待推送提交时同时展示累计待推送差异；分叉按 5.2 节处理。
2. 常规设置由当前浏览器随请求提供并校验；CLI 导出使用已保存的常规快照，无快照时要求显式指定外观值，不能静默遗漏。
3. 用户填写提交说明并确认。预览固定应用修订摘要、仓库 HEAD、远端分支 SHA（空仓库为不存在）、分支和导出内容摘要。仅本地提交可以离线进行，以当前本地 HEAD 为基准，并明确远端状态可能过期。
4. 确认时重新检查这些条件；提交并推送还需复查远端。发生变化返回预览过期。先在临时区生成和校验文件，再更新受管理目录并创建本地 commit。
5. 成功显示 commit SHA。推送仅使用普通 push 到已绑定分支，不 force push；推送期间远端被更新时由 Git 拒绝。界面分别显示“本地已提交”和“远程已推送”。

无差异时不创建空提交。用户也可以在外部 Git 客户端编辑、提交和推送文件；应用下一次操作前重新检查仓库状态。

首期要求整个工作区和索引干净，且不处于 merge/rebase/cherry-pick 状态。脏工作区列出阻塞文件并让用户自行处理，不自动 stash、reset、clean 或覆盖。应用只暂存和提交管理目录的变化；目录外文件保持原样。外部进程在操作期间修改仓库时中止，失败清理只针对本次写入且内容仍匹配的文件。

### 5.2 手动推送与获取

提供独立“推送”和“获取远程版本”操作。获取执行 fetch 并刷新远程提交列表，不 pull、不合并、不修改应用配置。已绑定仓库在网络不可用时仍可仅本地提交或恢复已获取的历史。

远端并发规则：

- 本地没有待推送提交且落后于远端时，可在生成提交预览前快进，随后重新生成差异；快进不能改动应用配置。
- 本地存在待推送提交且分支分叉时，停止推送，不自动合并或强制推送。
- 分叉时提供显式“基于最新远端重新生成提交”：先保留旧提交的本地备份引用，在独立暂存区基于最新远端生成当前配置差异，清楚展示将覆盖的远端配置变化；用户重新确认且远端未变后，才更新专用副本的分支并普通推送。取消或预览失败保留原分支和提交。该操作不自动重放旧提交，也不覆盖远端目录外文件。
- 推送期间远端变化导致拒绝时，保留本地提交，重新获取状态后处理。

认证失败、网络错误、受保护分支拒绝和分支分叉分别呈现。推送网络中断时显示“本地已提交，远端状态待确认”；重试前查询远端分支是否已包含本次 SHA，已包含则记为成功，否则重试相同提交或进入冲突处理，不重复创建提交。

### 5.3 从仓库恢复

1. 用户点击“从远端恢复”时先 fetch，列出绑定分支中的配置提交历史，展示提交说明、作者、时间、SHA、涉及类别和格式兼容性。离线时可显式选择已获取的本地历史，并标明远端状态未刷新。用户选择提交和恢复类别；分支/tag 在预览时解析成固定 commit SHA。
2. 系统直接读取该提交的 Git tree 到隔离临时目录，不 checkout 或改变绑定分支。只接受已提交快照，不从脏工作区恢复。
3. 检查格式兼容、文件摘要、路径、Schema、源码静态合法性和对象依赖，生成新增、更新、相同、缺失依赖和冲突清单。
4. 用户补充本机映射，查看差异并确认应用。仓库独有对象新增，同 ID 对象更新，目标独有对象保留；首期不因仓库缺少对象而删除本地数据。
5. 应用前保存本地恢复点，校验目标修订未变，在受控写入窗口内完成恢复。成功报告来源 SHA、变更统计和需要重新连接的服务。

恢复读取 Git 快照，不创建提交、移动本地或远端分支，也不自动推送。取消预览不改变应用数据。用户可选择更早提交再次恢复，或恢复本地恢复点；如需把历史状态重新发布到远端，在恢复后另行“提交并推送”，形成新的提交。恢复后不自动执行工作流、脚本或模型请求；Provider 登录、本机路径和浏览器连接按本机映射补齐。

## 6. 版本、依赖和冲突规则

- 对象按稳定 ID 匹配，不按名称匹配。同名不同 ID 的对象并存并提示；同 ID 不同对象类型拒绝。
- 已发布版本 ID 和内容摘要都相同则复用；相同版本 ID 内容不同为硬冲突，不能覆盖不可变版本，也不能悄悄改写引用。用户需在源仓库修正身份或回到应用发布新版本。
- 恢复已有版本可移动对象的当前发布版本指针；目标原版本仍保留，既有运行记录和引用不改写。导入新版本复用抽出的静态发布校验，不调用会生成新 ID、冻结当前 Provider 或要求当前编辑基线的普通发布入口。
- 版本 ID 必须保留，版本序号仅为本机展示顺序。新导入版本在事务内按对象当前最大 version_no 加一分配（同批按版本 ID 稳定排序）；已有版本保留原序号。不同设备产生相同序号但不同 ID 不构成冲突。同 ID 跨对象、跨版本类型或与目标草稿碰撞时阻止导入，不重写身份。
- 覆盖当前草稿必须出现在差异清单中；应用产生新的本地修订，不回退本机修订计数，也不伪造已有测试通过。
- 不合法但可保存的草稿允许恢复，并标记待修复；缺失文件、非法路径和格式错误始终阻止恢复。发布版本必须全部通过严格校验。
- 工作流引用的脚本版本必须在快照或目标中存在且摘要匹配；归档脚本可作为已有固定引用的依赖恢复，不开放新的引用。
- 工作流涉及的 Provider/模型和 Web Bridge 应用/工具必须校验；缺少依赖时在预览中加入对应类别，或阻止相关对象恢复。登录或浏览器在线状态不属于定义完整性条件。
- 一次恢复按所选范围整体成功或失败，不静默跳过出错对象。同 requestId 重试返回同一操作结果；相同 SHA 和映射以新 requestId 再次恢复时，重新比较目标内容。本地未改变时为无变化，不递增修订或重复建版本；本地后来发生编辑时重新应用快照。

## 7. 一致性与失败恢复

导出必须覆盖数据库定义、源码产物、Web Bridge 文件和浏览器常规值的同一份逻辑快照。服务端使用配置读写协调器和修订/摘要复查；预览后有编辑、发布、归档或工具配置变化时重新预览。

恢复前阻止新的定义写入和执行启动；首期在仍有工作流、脚本测试、Agent 生成或 Provider 验证活动时拒绝应用并提示稍后重试。所有相关写入口必须遵守同一锁，不能只禁用前端按钮。

### 7.1 协调器和活动边界

新增 `ConfigWriteCoordinator`，服务内所有定义写入、产物清理及执行启动须通过它。覆盖工作流创建/保存/发布/删除、脚本创建/修改/发布/归档/恢复/清理、Agent 提案应用、Provider 保存/模型目录刷新及验证、Bridge 应用/环境/工具修改与直接工具调用，以及运行和测试队列的启动。异步发布、模型发现和 Agent 任务从接受到最终写入均登记活动租约；不能仅在 HTTP 请求开始时检查锁。已有 queued/running/cancel_requested 运行、未结束测试/生成/验证/工具调用均阻止恢复。

恢复获取排他窗口后检查活动数、目标摘要及 revision，并阻止新活动；检查和关闭入口必须为同一协调动作，不存在“检查空闲后又启动任务”的间隙。普通写操作有短写入窗口和配置代次；导出在读窗口内复制所有定义及必要产物到隔离区，异步校验使用该副本，预览确认再复查配置代次和完整摘要。Git 网络请求不占用配置排他窗口。多进程由现有 data-dir DirectoryLease 排他约束；CLI 校验独立目录不打开应用数据库，访问运行实例的导出通过服务 API。

### 7.2 持久化恢复状态机

数据库与文件系统不能靠一个 SQLite 事务实现整体原子性。采用“提交前保留旧状态，数据库提交后补齐新状态”的确定性协议；数据库已提交后不直接覆盖数据库文件回滚，用户恢复旧状态通过恢复点生成新操作完成。

| 阶段 | 持久化动作 | 中断后处理 |
| --- | --- | --- |
| accepted / validating | 保存 requestId、请求摘要、operationId；解析、映射及静态校验 | 尚未进入应用阶段，可以重新校验或标记失败，业务数据不变 |
| prepared | 持有排他窗口复查；保存完整恢复点、最终导入计划、新文件内容与摘要；文件及目录 fsync 后写日志 | 无数据库回执则保持旧配置，清理仅属于本操作且未引用的暂存文件 |
| db_committed | 在一个 Store.command 同步事务内写入全部业务行与回执；事务外的编译/网络操作必须预先完成 | 以数据库回执判断提交事实，即使文件日志仍为 prepared 也进入补齐新状态 |
| files_installed | 按日志逐个原子替换 Bridge、常规设置、本机映射等文件；每次验证内容摘要并记录进度 | 重试已安装文件为无变化，未完成项从持久化暂存内容补齐 |
| completed | 重载 Provider/Bridge 缓存、重置连接状态，验证最终定义摘要；持久化结果后开放业务入口 | 重试返回原结果；缓存可在重启后重建 |
| recovery_required | 提交后文件丢失/损坏、安装失败或结果校验失败 | 保持维护状态，提供操作状态与显式恢复重试；不得开放相关读取和运行以暴露混合配置 |

不可变源码产物先写入新内容寻址路径并 fsync，不替换旧产物；事务只引用已持久化路径。操作日志使用临时文件、fsync、rename、父目录 fsync，设置目录 0700、文件 0600。回执 scope 固定为 `config-git:restore`，requestId 标识该次应用；request_hash 绑定最终计划，result_json 保存 operationId、planHash、恢复点 ID 和数据库阶段结果。回执只证明数据库阶段提交，API 最终成功以文件阶段及 completed 日志为准。

启动时在 `Store.recoverBusiness()`、Provider/Bridge 初始化及运行/测试队列启动之前，检查未完成日志和回执并执行恢复；`config-git/staging` 独立于现有通用 staging，不能被业务恢复清理。异常情况下仅开放健康、操作状态与恢复重试所需接口。数据库审核详见 [schema-review.md](schema-review.md)。

恢复点包含受影响对象原定义、指针、草稿、设置文件、本机映射和必要产物的独立副本，存于 Git 目录外并限制访问权限，不仅保存可能被清理的路径引用。首期手动清理，未完成恢复引用的恢复点不可删除。恢复点可通过同一预览/应用协议恢复；目标独有对象及已导入的不可变版本仍保留，恢复点恢复的是受影响配置，不删除运行历史或整体替换数据库。

### 7.3 浏览器偏好与服务缓存

浏览器保存随机 clientId、偏好 revision 和已消费 operationId；提交预览携带 theme 与 revision，确认时必须再次提交并比对，变化则重新预览。服务端仅在提交/恢复成功时记录常规快照，CLI 无快照时必须显式提供 theme。

外观恢复在服务端记录 clientId、operationId、原偏好 revision 和目标 theme。发起浏览器在 completed 后应用并回执；刷新或关闭后重连仍可消费，重复回执无副作用。若用户在等待期间已改变偏好 revision，显示冲突供用户选择应用或保留，不静默覆盖；其他 clientId 不消费该记录。CLI 恢复常规值只更新服务端快照，浏览器显式领取并确认后应用。清除浏览器存储导致 clientId 丢失时提示重新领取，不宣称已改变其他设备偏好。

Bridge 恢复后重新加载配置并重新握手，bound/tabAvailable 重置，不自动安装扩展、登录或绑定标签页；Provider readiness 和验证缓存失效，不修改外部认证文件。恢复前的会话记录保留，后续继续对话须经过现有 Provider 修订/连接身份检查。

## 8. 页面与接口草案

“设置 → Git 配置存储”未绑定时展示远端接入表单和连接检测；绑定后展示仓库、分支、remote、工作区状态、领先/落后或分叉状态、待推送提交、最近操作和本地/远程 SHA，提供“提交并推送”“仅本地提交”“推送”“获取远程版本”“从远端恢复”“本地历史”和“解除绑定”入口。提交和恢复共用按类别分组的差异预览；不可变版本冲突、本机映射缺失和格式不兼容为明确阻塞项。

| 方法 | 拟新增路径 | 用途 |
| --- | --- | --- |
| POST | `/api/config-git/remote/check` | 检测认证和读取连接，返回远程分支；不宣称已验证推送权限 |
| POST | `/api/config-git/bind` | 创建专用本地副本、检查配置目录并保存远端绑定 |
| GET | `/api/config-git/repository` | 查询绑定信息 |
| POST | `/api/config-git/unbind` | 解除绑定，保留应用配置、副本和恢复资料 |
| GET | `/api/config-git/status` | 查询工作区、分支领先/落后状态、待推送提交和操作状态 |
| POST | `/api/config-git/commit-preview` | 生成配置快照和 Git 差异；显式重新生成模式支持分叉处理预览 |
| POST | `/api/config-git/commit` | 按预览 token 手动提交，可选推送；重新生成模式先保留旧提交引用 |
| POST | `/api/config-git/fetch`、`/api/config-git/push` | 显式获取或推送 |
| GET | `/api/config-git/commits` | 分页查询可恢复提交 |
| POST | `/api/config-git/restore-preview` | 校验固定 SHA，生成恢复计划 |
| POST | `/api/config-git/restore` | 应用已确认计划 |
| GET | `/api/config-git/operations/:id` | 查询阶段、结果和失败原因 |
| POST | `/api/config-git/operations/:id/recover` | 重试未完成恢复的持久化阶段，不创建新的业务应用 |
| GET / DELETE | `/api/config-git/recovery-points` / `/api/config-git/recovery-points/:id` | 列出或手动删除未被未完成操作引用的恢复点 |
| GET / POST | `/api/config-git/general/pending` / `/api/config-git/general/ack` | 按 clientId 读取待应用偏好及回执，CLI 快照领取需显式确认 |

写操作携带 `requestId`，确认操作携带绑定内容、目标修订、仓库身份及有效期的预览 token。同请求重复提交返回同一结果，相同请求 ID 不同内容拒绝。长操作返回 HTTP 202、operationId 和 statusUrl，客户端断线不代表操作取消；重连查询最终状态。

预览 token 为服务端保存的随机 ID，有效期 30 分钟，绑定最终计划摘要、bindingId、源 SHA、HEAD、远端观测 SHA、类别、本机映射摘要、应用代次及浏览器偏好 revision。映射和类别变化须重新预览；重启使未确认预览失效，不影响已接受操作。恢复点预览使用 `source: { kind: recovery-point, id }`，Git 预览使用 `source: { kind: git, sha }`。恢复不会因远端新增提交而改变已固定源 SHA，但绑定身份、目标配置及专用副本 HEAD 变化须重新预览。

差异每项包含 category/objectId/versionId/path、changeType、before/after 和阻塞原因；已标记敏感字段只显示字段名及变化状态，绝不回显值。错误码至少覆盖 PREVIEW_EXPIRED、CONFIG_BUSY、VERSION_ID_CONFLICT、DEPENDENCY_MISSING、LOCAL_MAPPING_REQUIRED、FORMAT_UNSUPPORTED、DIRTY_REPOSITORY、REMOTE_DIVERGED、AUTH_FAILED、PUSH_REJECTED、REMOTE_UNKNOWN、RECOVERY_REQUIRED；冲突返回 409，校验失败 422，维护状态 503。分页历史用固定起点 SHA 与游标，避免 fetch 后翻页漏项。

Git 命令默认超时 30 秒，clone/fetch/push 为 120 秒；终止整个子进程组。错误输出最多 64 KiB，状态/引用输出最多 4 MiB，读取 tree 以文件数、单文件和总大小限额独立控制。v1 快照上限 10000 文件、64 MiB，单对象继续遵守现有领域限制；超限须明确报错。Git 状态和差异使用机器可解析及 NUL 分隔格式，预览全量差异分页可查，截断不能被显示成完整预览。

Git 调用使用参数数组和固定子命令，不拼接 Shell；限制超时、输出大小和并发，每个仓库同时一个写操作。关闭仓库 hooks、外部 diff/textconv、自动子模块执行等隐式执行入口；不加载仓库提供的脚本。clone 使用不检出模式，读取 tree 和生成提交优先采用 Git 对象接口与独立索引，避免属性驱动的 clean/smudge/filter 或 LFS 隐式执行。工作区需要物化时从已校验 Git blob 写入，不调用可触发仓库过滤器的默认 checkout。仅接受 SSH/HTTPS 地址，拒绝本地路径、file/ext 等协议和以选项开头的输入，分支通过 check-ref-format 校验。保留本机认证链所需配置，但不继承环境注入的仓库位置、索引和命令级 Git 配置；签名等非认证外部执行入口默认关闭。凭据只由已配置的本机 Git 认证链处理，输出和日志需要脱敏。

## 9. 数据与模块影响

拟新增以下模块，以及设置页入口；它们调用现有领域校验和持久化接口，禁止通过导入 SQL 文件恢复业务配置。

| 模块 | 职责 |
| --- | --- |
| `GitRepositoryService` | 连接检测、克隆、分支状态、fetch、commit、push、按 SHA 读取文件和绑定生命周期 |
| `ConfigSnapshotService` | 稳定序列化、静态脚本解析、manifest 摘要、差异和依赖校验 |
| `ConfigRestoreService` | 恢复预览、本机映射、恢复点、写入协调和失败恢复 |
| `ConfigWriteCoordinator` | 统一定义写入、活动登记、排他应用窗口及维护状态 |
| 领域导入接口 | 接受固定对象/版本 ID，分配本机序号，复用静态校验，按计划更新草稿及指针；不调用普通发布流程 |

```text
  local-mappings.json
```

`binding.json` 保存仓库地址、分支、配置目录和副本标识，不保存认证秘密。最近成功推送和恢复的 SHA 记录在操作日志中，实际远端状态以 fetch 结果为准。绑定、提交、推送、分叉重新生成和解除绑定共用互斥控制；耗时操作返回 operation ID，刷新页面后可以继续查询。

提交审核的首期方案不新增数据库表、字段、索引、触发器或迁移，也不提升数据库版本：仓库绑定、常规设置快照、本机映射、操作日志和恢复点使用 data-dir 下独立文件，工作流/脚本/Provider 沿用现有存储。数据库审核仍是用户明确要求的编码前置阶段，审核对象包括现有表写入、版本唯一性、草稿身份、回执与跨存储恢复协议，详见 [数据库审核方案](schema-review.md)。审核通过后按本文完成全部编码，不在每个模块结束时重新请求开始下一模块。若实施发现必须调整已审核数据库方案，先补充具体差异并重新审核，不绕过[根目录规则](../../../AGENTS.md)。

这不是数据库备份或数据版本迁移工具；恢复前目标 Orchard 必须处于自身可用的数据库版本。未知快照版本拒绝并提示兼容版本，不自动触发数据库迁移。

## 10. 验收标准

1. 一次提交包含常规、Provider、Web Bridge、工作流及脚本定义；多文件源码、布局、模型状态、工具定义和固定脚本引用可完整往返。
2. 相同配置连续导出无文件差异；无差异不创建提交；普通保存不触发 Git 或网络操作。
3. SSH/HTTPS 远端绑定可完成连接检测、分支选择和专用副本创建；缺失认证、未知 SSH 主机、空仓库和无推送权限均有明确状态。空仓库首次推送创建目标分支；已有仓库保留配置目录外文件。
4. 外部编辑声明式脚本并刷新 manifest 后可恢复；含可执行表达式、路径越界、符号链接、摘要损坏或未知格式时不写入任何配置。
5. 新环境可按预览补全本机映射，恢复定义后明确提示登录和 Bridge 重新连接；凭据、浏览器会话、检测状态和运行历史不进入 Git。
6. 历史 SHA 恢复可回退设置、草稿与当前版本指针，保持旧发布版本不变；目标独有对象不被删除。
7. 缺失固定脚本版本、Provider/工具依赖以及相同版本 ID 内容冲突均阻止应用，并定位到对象和字段。
8. 提交/恢复预览后发生编辑或仓库 HEAD 变化时返回冲突；脏仓库和 Git 冲突不会被自动清理。
9. 针对数据库提交前后、文件替换前后和进程重启注入故障，可恢复为完整旧状态或完整新状态，期间不启动新运行；重复请求不重复建对象或版本。
10. 恢复不会执行仓库配置代码、业务脚本、Git hook 或真实模型请求；差异和日志不回显已标记敏感值。
11. 验证浏览器偏好导出、CLI 无常规快照、浏览器在恢复期间断线和 Bridge 重连行为，避免设置被静默遗漏。
12. 受保护分支拒绝、远端并发更新、分支分叉和推送中断均保留本地提交；重试先检查远端是否已包含 SHA，不重复提交、不 force push。
13. 分叉重新生成必须保留旧提交引用、展示相对最新远端的差异并重新确认；取消不移动原分支，目录外文件不被覆盖。
14. 已有有效快照提供提交/恢复选择；无效或不兼容配置目录不能被静默覆盖。解除绑定保留应用配置、未推送提交和恢复资料。
15. 网络不可用时可仅本地提交或恢复已获取历史，并明确状态时效；远端恢复固定 SHA，不移动分支，跨设备恢复验证全部固定版本依赖。

16. 两个设备产生相同本机版本序号、不同稳定 ID 时可合并导入；已有版本序号不变，固定引用不改写。源发布版本 ID 与目标草稿 ID 碰撞、版本归属错误与同 ID 内容冲突均可定位。
17. 未发布工作流、草稿基线版本、隐藏模型、归档脚本依赖可以往返；空草稿/空发布指针按保留规则显示，不隐式删除。
18. 同请求重试与新请求再次恢复区分正确；恢复后本地编辑，再恢复相同 SHA 能重新应用配置；完全相同内容不增加修订。
19. 恢复点经过产物清理后仍可独立读取并恢复；待恢复点不可删除。偏好回执重复、用户期间修改偏好、多浏览器和 CLI 领取均符合 7.3 节。
