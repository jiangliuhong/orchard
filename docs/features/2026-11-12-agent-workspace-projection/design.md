## 1. 核心结论

> 数据库是唯一事实源；workspace 是平台维护的只读项目投影；Agent 读取文件并提出方案；用户确认确切变更后，由平台统一应用到数据库并同步文件。

工作流、脚本、浏览器工具在同一个项目目录中呈现。维护 Agent 的使用体验接近“在该目录运行 Pi 并创建原生会话”，但 **Agent 不直接编辑项目文件，也不直接操作数据库**。

所有文件写入均由平台负责，包括页面手工修改、Agent 提案应用和版本发布引起的投影更新。Agent 可通过 Orchard 提供的 MCP 或 CLI 发起受控请求；两种入口必须复用同一个应用服务，第一版选择 MCP stdio，不同时实现通用 CLI；仅优先适配 Pi，未通过安全能力验证的 Provider 保持禁用。

## 2. 目标与非目标

### 2.1 目标

- 统一呈现工作流、脚本、浏览器工具的定义、源码、版本与引用身份，使 Agent 可通过原生文件读取和搜索理解业务资产。
- 所有维护对话共用一个 workspace，不按会话复制规则、Skills 或业务文件。
- 原生 CLI 自行管理对话上下文，不由平台重放消息、拼接完整草稿或生成历史摘要。
- 保留提案、用户确认、revision 校验、权限和现有发布边界，降低上下文适配及工作目录管理复杂度。
- 将数据库与文件的关系固定为“事实源 → 可重建投影”，不引入两套同等权威的配置。

### 2.2 非目标

- 不让 Agent 直接 write/edit workspace，不开放通用 SQL 或宿主任意路径写入工具。
- 不监听目录后自动反向导入配置，不把任意磁盘修改当成用户授权。
- 不在第一版实现 Git worktree、自动合并、多 Agent 并行修改或双向实时同步。
- 不把 workspace 当成源码备份、会话历史存储或业务运行目录。
- 不把既有九表方案、通用 WorkspaceService 或知识安装状态机原封不动作为新方案的实施前提。

## 3. 职责与数据流

```text
平台数据库 + 已有不可变源码产物 + 安装包内置规则
                    ↓ 平台生成/同步
       agent/workspace：只读业务项目
                    ↓ 读取、搜索
             Pi 原生会话
                    ↓ 提交候选变更
        平台保存不可变提案并生成 diff
                    ↓ 用户确认确切提案
          Orchard 工具 / 页面应用入口
                    ↓ 统一应用服务
       校验权限、确认凭证、revision、依赖
                    ↓
       数据库事务提交 + 登记待同步状态
                    ↓
            平台更新 workspace
                    ↓
          返回应用结果与投影同步状态
```

| 模块 | 职责 |
|---|---|
| Workspace 投影 | 从数据库和受管产物生成可读文件；记录投影状态；损坏时重建 |
| 原生会话适配 | 指定 cwd、创建/准确恢复 session、限制工具、取消与释放进程 |
| 提案服务 | 固化候选变更、展示 diff、保存真实用户确认，禁止确认后替换内容 |
| 统一应用服务 | 检查权限和基线、幂等应用、事务更新数据库、同步投影 |

平台仍可保存展示用消息与任务记录，但不将它们反向构造为模型历史。Provider 的 CLI 参数、session 标识和文件格式继续由适配器封装。

## 4. 数据目录结构

以下为目标布局；`<id>` 是平台分配或校验后的安全资源标识，不直接拼接任意用户输入。

```text
<orchard-data>/
├── workbench.db                         # 配置、提案、确认、任务、会话引用及同步状态
├── workbench.db-wal
├── workbench.db-shm
├── agent/
│   ├── workspace/                       # 所有维护对话共用，Agent 只读
│   │   ├── project.json                 # 派生资源/版本/依赖路径索引
│   │   ├── AGENTS.md                    # 平台内置维护规则
│   │   ├── docs/                        # 内置场景说明
│   │   ├── .agents/
│   │   │   └── skills/                  # 内置 Skills；是否生效由适配器验证
│   │   ├── workflows/
│   │   │   └── <workflow-id>/
│   │   │       ├── resource.json        # 稳定身份、草稿列表、当前发布版本
│   │   │       ├── drafts/<draft-id>/
│   │   │       │   ├── resource.json
│   │   │       │   ├── workflow.json
│   │   │       │   └── scripts/         # 工作流内嵌源码，不复制脚本库源码
│   │   │       └── published/           # 当前生效版本，同类文件结构
│   │   ├── scripts/
│   │   │   └── <script-id>/
│   │   │       ├── draft/
│   │   │       │   ├── resource.json
│   │   │       │   ├── script.json
│   │   │       │   └── src/
│   │   │       ├── published/           # 当前发布版本，同类文件结构
│   │   │       └── versions/<version-id>/ # 仅实际引用的历史固定版本，同类结构
│   │   └── browser-tools/
│   │       └── <application-id>/
│   │           ├── resource.json       # 应用级身份与配置 revision
│   │           └── <tool-id>/
│   │               ├── resource.json
│   │               └── tool.json
│   ├── sessions/
│   │   ├── pi/                         # Pi Adapter 管理的原生历史
│   │   └── codex/                      # Codex Adapter 管理的原生存储
│   └── tmp/                            # 投影暂存或确有需要的任务临时文件
├── artifacts/                          # 沿用既有不可变源码和产物存储
├── runs/                               # 业务执行资源，不向维护 Agent 暴露
├── project-git/                        # 外部项目缓存、分析快照与私有进程资源
├── config/                             # 平台配置；不整体暴露给维护 Agent
├── secrets/                            # 密钥材料，禁止 Agent 访问
├── backups/
└── migrations/
```

约定：

- 工作流呈现全部可编辑 `drafts/<draft-id>/`，脚本仅有一个 `draft/`；`published/` 仅在当前发布状态存在时生成。固定维护对象必须绑定确切草稿，不取“最近草稿”。浏览器工具不虚构发布版本。
- 第一版不导出全部历史；当前配置引用的其他固定脚本版本按需呈现于 `versions/<version-id>/`，只读且准确。具体发现、去重、预算和不完整草稿规则见实施契约第 1、2 节。
- `resource.json` 提供稳定 ID、资源类型、版本标识、revision 和必要的只读/编辑范围信息，不含凭据值、宿主内部路径或授权令牌。应用时以数据库为准，不信任 Agent 回传或磁盘中的 revision。
- 会话历史、提案、确认记录和同步状态不写入 workspace；提案等平台记录继续以数据库为准，不另建一套 JSON 真相。
- `tmp/` 按需使用，不为每个 turn 固定创建空目录；不再出现“场景临时目录里再套一层 .agent-*”的重复分配。
- 项目分析所需的外部 Git 快照、缓存和运行产物保持独立，不混入维护投影，也不随对话删除。

## 5. 原生 multi 对话

工作流、脚本、浏览器工具维护入口使用原生 multi。

1. 平台检查身份、维护对象、Provider/模型和 workspace 同步状态。
2. 以 `<orchard-data>/agent/workspace/` 为 cwd，创建全新原生 session，或按平台保存的准确引用恢复指定 session。
3. Agent 读取项目文件、搜索关联资源，根据用户需求提交候选变更。跨资源可见性不等于跨资源写入授权。
4. 平台固化提案并展示 diff，用户确认后才能应用。
5. 页面确认或 Agent 应用工具登记已确认的应用请求；活动轮次中仅返回 queued。轮次结束并确认 Provider/工具进程退出后，由平台校验并应用；空闲时直接处理，不为应用另启模型。
6. 每轮关闭进程但保留准确原生引用。后续人工消息恢复该 session，不重新注入完整源码、历史或草稿；真实结果由平台页面及 proposal_status 展示。

共用 cwd 不共用对话上下文，也不意味着可以通过“恢复该目录最近会话”定位对话。进程可以回收，原生会话引用必须准确保留。

维护任务的文件写入仅通过平台进行，不以 Pi 的 edit/write 工具直接落盘。原生读工具、规则加载和平台应用工具的具体接线必须单独验证。

## 6. single 任务

single 表示一个逻辑轮次，不等于一次模型 API 调用；该轮中可以包含多次推理和允许的工具调用。

### 6.1 只读分析

需要读取平台资产的单次分析可以使用共享 workspace：

```text
创建全新非持久会话 → 读取文件/分析 → 返回结果 → 关闭进程
```

以 Pi 为例使用 RPC 与 `--no-session`，不传 session 恢复引用，不为任务复制 workspace。具体启动参数和加载范围以适配验证为准。

### 6.2 生成修改提案

```text
读取当前资源与 revision → 提交不可变提案 → single 结束
                         ↓
                    用户确认提案
                         ↓
               平台直接应用并同步 workspace
```

single 结束后的确认应用由平台执行，不为调用一次应用工具再次启动模型，也不把重新启动的任务伪装成原 single 的继续。

不采用“保持 single 工具调用挂起、一直等待用户确认”作为第一版默认流程，避免引入额外的进程占用、超时和恢复复杂度。

### 6.3 其他 single 场景

普通工作流 Agent 节点、Git 提交说明、模型验证等，不因为维护 workspace 存在就默认获得全部平台资产权限。无需资产读取时使用隔离临时 cwd；外部项目分析使用固定 SHA 的项目快照和独立资源。

## 7. 不可变提案与用户确认

用户确认的对象必须是确切变更，而非一句笼统的自然语言方案。

接口与载荷基线见实施契约第 3、4 节（尚未生产接入）：

- `orchard.submit_proposal(...)`：提交候选变更，平台校验并固化，返回 proposalId；不应用配置。
- 页面展示提案 diff，由真实用户确认对应 proposalId。
- `orchard.apply_proposal(proposalId, requestId)`：登记已确认提案的应用请求，不接受替换正文；活动读取期间返回 queued，不声称已应用。
- `orchard.proposal_status(proposalId)`：查询真实业务回执及投影同步状态，不伪造先前工具结果。

平台保存提案内容、目标资源、基线 revision、内容 hash 和确认归属。Agent 自报 `confirmed: true`、伪造自然语言“用户已同意”或调用提交工具，都不能代替页面确认。

应用必须校验：

1. 当前主体、固定维护目标、提案目标与允许动作匹配。
2. 用户确认绑定的提案内容没有变化；提案未撤销、未删除且仍可应用。
3. revision 与当前数据库状态一致，事务内再次 CAS；冲突要求重新读取并生成提案，不自动覆盖或合并。
4. JSON Schema、源码、资源 ID、依赖和敏感内容符合平台约束；Agent 不能凭文件布局绕过校验。
5. 涉及删除时检查依赖，并明确展示删除后果；文件缺失不自动触发数据库删除。
6. 同一 requestId 幂等；丢失响应后查询既有结果，不重复创建版本或重新执行应用。

应用成功与正式发布仍沿用各场景原有边界，不因工具接入而自动发布、执行脚本或调用浏览器业务端点。

## 8. 数据库与 workspace 同步

SQLite 事务不能与文件系统组成原子提交，不承诺真正“同时写成”。采用单向投影：

1. 读取并校验已确认的不可变提案，准备所需不可变源码产物。
2. 数据库事务中校验 revision，应用变更，并登记目标投影版本/待同步状态。
3. 根据已提交配置生成确定的文件内容，使用受管暂存与原子文件替换更新 workspace。
4. 校验目标投影已完整就绪后标记同步完成，允许依赖该投影的新任务继续。

若数据库提交失败，不修改 workspace。若数据库已提交而文件同步失败，明确返回“已应用，workspace 待同步”，保留应用回执；不得笼统当作未应用并重试整份配置。

服务重启时，先修复未完成投影再受理相关 Agent 任务。投影损坏或存在非平台改动时，从数据库、受管产物和安装包重建，不反向采纳磁盘内容。

所有业务写入口，包括页面修改、Agent 应用、发布、恢复和删除，都必须触发同一投影同步机制。备份与配置 Git 的权威内容继续遵循现有规范，不把派生 workspace 再当成一份用户配置纳入同步。

## 9. 并发与资源所有权

第一版采用保守、可解释的规则：

- 一次仅运行一个共享项目维护任务，平台写操作串行；不设计多个 Agent 并行修改和自动合并。
- 外部项目分析和不读取共享资产的 single，不必受共享维护任务的串行限制。
- 应用提案和更新投影时，需要阻止与文件读取交叉，不能让 Agent 读到跨文件混合版本。
- 页面并发修改必须排队到安全边界，或拒绝并明确提示；最终仍以数据库 revision 校验防止覆盖。
- 应用工具不能等待自己持有的“整个轮次读锁”。实现时需选择工具执行安全边界或轮次结束后的同步；如果不能证明原生文件读取已经停止，就不能边更新目录边继续该任务。
- 临时资源只设一个明确的分配/释放所有者；删除或释放会话不能删除共享 workspace、其他会话或业务资产。

首版采用活动轮次仅登记 queued 应用、每轮关闭进程后更新文件、页面业务写入忙时拒绝的边界，见实施契约第 5 节。真实 CLI 空闲关闭及原生读取越界已有验证；范围工具/MCP/活动子进程关闭仍须实测，不以提示词约定代替并发控制。

## 10. 权限与敏感信息

- cwd 不是沙箱；平台提示词和只读权限位都不能单独构成安全边界。
- 禁止 Agent 直接修改文件，需通过 Provider 工具策略和可验证的文件访问/进程边界实现。受控 Orchard MCP/CLI 不意味着可以开放任意 shell、用户扩展或第三方工具。
- workspace 只包含允许该维护主体读取的业务定义及源码。共享目录意味着原生文件读取通常可遍历整个投影；若未来存在不同可见范围，不能只靠应用工具的 authorizer 假装实现了读取隔离，必须重新划分投影或读取边界。
- 不投影密钥值、加密字典值、Cookie、运行输入输出、跨资源日志、模型凭据、数据库文件或工具授权令牌；历史源码中疑似硬编码敏感值也须阻止或脱敏并明确说明。
- 工具认证通过独立受控通道传递，绑定当前主体/对话，不放入共享文件或消息历史。CLI 工具不能凭本机执行身份自动获得任意提案的应用权限。
- 规则、说明、源码和注释均是不可信任务数据；实际授权由平台执行。

## 11. 与现有实现及旧 feature 的关系

当前生产仍使用旧业务 Service、分散的 cwd 和部分历史重放。已有统一 Runtime、持久化、原生删除及知识模块是可复用候选，不代表本方案已接入。

本方案替代前置设计中以下方向：

| 前置方向 | 新方向 |
|---|---|
| 共享 cwd 只存内置规则/Skills | 共享 cwd 同时呈现受控业务配置与源码投影 |
| 跨资源源码主要通过专门查询工具读取 | 优先原生文件读取/搜索；确有需要再保留精简查询接口 |
| 维护 Agent 不允许任何平台写工具 | 允许提交/应用受控提案；真正写入仍由平台执行并验证用户确认 |
| 每轮模型输出大型 JSON 作为独立场景适配结果 | 单目标资源级不可变提案与 diff，载荷见实施契约 v1 |
| 较重的通用工作区、知识安装和资源租约体系 | 优先单投影、明确所有者和最小必要恢复流程，不机械照搬旧抽象 |

继续保留原生上下文、不重放历史、single/multi 区分、准确 session 引用、进程退出确认、幂等、revision 校验以及直接删除会话时的安全边界。

旧方案的数据库审批只适用于其已审核结构，不自动授权新提案/确认/同步模型的结构变更；本方案也不授权直接重置已有 Agent 数据。

## 12. 数据与接口影响、实施前确认项

涉及提案及确认、queued 应用回执、投影目标代次/同步状态、原生会话引用与浏览器配置事实源迁入数据库。[数据库审核稿](./database-review.md)已列出 8 个拟新增表及约束、索引、触发器、迁移与保留方案，**结构设计已批准，仅授权实现与隔离测试；未激活生产迁移，不执行旧 v11 重置步骤。**

以下确认项已形成实施契约及审核材料，数据库结构已获批准；实际迁移确认和真实工具链安全验收仍为独立门槛：

1. 单固定目标的资源级提案，正文/快照/预算及字段白名单见实施契约第 3 节；不接受任意宿主文件补丁。
2. 首选 Pi + MCP stdio，通过可信范围工具边界和独立 grant 授权；原生 read 越界实测及 Provider 阻断门禁见 CLI 验证。
3. 用户确认登记应用请求；multi 活动轮次只 queued，进程已回收时由平台直接应用，single 不再调用模型。
4. 历史固定脚本依赖按 versions/<versionId> 呈现，多草稿按 drafts/<draftId> 保留；仍需下一阶段改造生成器。
5. 每轮关闭原生进程并确认静默后才同步文件；活动维护期间页面业务写入拒绝并保留输入，不在工具调用中等自己持有的读锁。
6. 复用已有业务表/产物/回执，新增受审维护记录并把浏览器声明配置迁入 DB；旧会话保留，不自动跨 cwd 恢复，目录和数据迁移执行另行预览确认。

## 13. 验收标准

- 所有维护对话使用同一 workspace；创建多个对话不复制规则、业务文件或 Skills。
- Pi 在该 cwd 创建/准确恢复指定会话；不同会话不串上下文，不恢复“最近会话”。
- Agent 可读取授权范围的工作流、脚本与浏览器工具定义和源码；固定依赖的版本准确，超限与缺失明确返回。
- Agent 直接 edit/write、任意 SQL、越界路径、伪造用户确认、未确认提案应用等负例被拒绝。
- 用户确认后只能应用该份不可变提案；revision 冲突不覆盖页面修改，不自动合并。
- 页面和 Agent 应用均通过同一服务更新数据库与投影；文件缺失不自动删除资源。
- 数据库已提交而文件同步失败时，应用不重复、状态可查询、重启可修复；投影未就绪不允许依赖新文件的任务继续。
- 并发维护、页面修改、文件读取和投影更新不会产生混合版本或读写锁自等待。
- single 使用全新非持久上下文；返回提案后即可结束，确认应用无需再次调用模型。
- 非维护 single 和项目分析不默认获得整个配置投影权限；共享 workspace 不作为会话清理目标。
- 不泄漏凭据、运行数据、会话授权和原生存储内部路径；协议夹具通过不冒充真实 CLI 能力验证。
- 实际目录迁移、数据库变更和破坏性重置前具有独立审核/确认；本文件完成不视为实施完成。
