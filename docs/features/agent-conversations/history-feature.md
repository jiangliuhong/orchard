# 与 Agent 创作：历史对话与工作流绑定

## 背景

“与 Agent 创作”当前以草稿为中心，但用户很难区分不同的创作过程，也无法在离开页面后准确回到上一次讨论。一次工作流可能经历需求梳理、节点设计、调试和发布准备等多个阶段，这些过程需要保留为可查找、可恢复的历史对话。

本 feature 为每个工作流草稿提供对话历史。对话属于工作流草稿，工作流复制、发布和删除时遵循明确的生命周期规则；对话本身不改变已发布版本，也不被工作流运行复用。

## 目标

- 支持创建一个全新的创作对话。
- 支持继续当前工作流的已有对话，并恢复上下文。
- 支持查看历史对话，区分当前、已归档和需要重建的会话。
- 支持归档不再使用的对话，保留消息和审计信息。
- 保证对话始终绑定到唯一的工作流草稿，避免跨工作流串入上下文。
- 在刷新页面、服务重启或重新打开工作流后，能够恢复可恢复的对话状态。

## 用户故事

- 作为创作者，我可以点击“新对话”，从当前草稿重新开始讨论，而不删除之前的设计过程。
- 作为创作者，我可以在工作流再次打开时点击“继续对话”，看到原来的消息并继续生成。
- 作为创作者，我可以在历史列表中找到某次调试对话，并阅读其完整消息。
- 作为创作者，我可以归档已经结束的对话，让当前列表保持简洁。
- 作为创作者，我可以明确知道当前对话使用的 Provider、模型和上下文状态。
- 作为创作者，我不会因为切换到另一个工作流而看到或发送到错误的对话。

## 绑定关系

关系链固定为：

```text
工作流（workflow）
  └── 草稿（draft）
        └── 对话（conversation）
              ├── 轮次（turn）
              └── 消息（message）
```

- 对话必须绑定一个 `draftId`，不能直接绑定已发布版本。
- 一个草稿可以拥有多个对话，但同时最多一个“当前对话”。
- 工作流的不同草稿拥有独立对话空间；切换草稿不得复用当前对话。
- 发布工作流只固化流程定义、模型配置和输出配置，不携带对话引用。
- 从已发布版本复制为新工作流时，不复制原工作流的对话。
- 删除草稿或工作流时，在同一清理流程中删除其对话、轮次和消息；有活动轮次时先拒绝删除。
- 运行工作流、运行中的 Agent 节点和模型验证不读取或写入创作对话。

## 核心交互

### 对话入口

创作区左侧显示对话选择器，包含：

- 当前对话：默认打开，可继续发送消息。
- 历史对话：按最近活动时间倒序展示。
- 已归档：默认折叠，可展开查看。
- 需要重建：可以阅读，但必须先创建新上下文才能继续。

每项至少显示标题、最近活动时间、状态、Provider / 模型和最后一条用户消息摘要。标题由首条用户消息生成，用户可以手动修改；标题修改不影响消息内容和上下文。

### 新对话

点击“新对话”后：

1. 检查当前草稿是否有未保存修改；有修改时先保存，保存失败则不创建。
2. 检查当前对话是否存在排队、执行中或取消中的轮次；存在时拒绝操作并提示等待。
3. 创建新的当前对话，默认使用当前 Provider、模型和多轮模式。
4. 保留旧对话及其全部历史；旧对话变为历史状态。
5. 清空编辑区中的消息视图，但不清空草稿文件。

新对话不读取旧对话的原生后端上下文。若用户选择“带摘要重建”，必须明确展示摘要来源和“这是新上下文”的提示。

### 继续对话

点击当前或历史列表中的“继续对话”时：

- 当前对话直接恢复消息列表和可用上下文。
- 已完成、空闲的历史对话可以被设为当前对话继续；切换后原当前对话自动转为历史状态。
- 已归档对话默认只读，需先点击“恢复对话”；恢复后成为新的当前对话，并记录恢复时间。
- `needs_rebuild` 对话不能直接发送消息，只能执行“重建上下文”。重建会创建新的对话或新的后端上下文，并保留原会话作为诊断历史。
- 不允许重新激活已删除的对话。

继续对话时，服务端必须重新校验草稿归属、Provider / 模型配置和对话状态，不能仅依赖前端传入的对话 ID。

### 会话归档

对话菜单提供“归档”操作：

- 归档前需要确认；归档不会删除消息、轮次、模型信息或审计数据。
- 有排队、执行中或取消中的轮次时不可归档。
- 归档后不能直接发送消息，也不能作为默认当前对话。
- 用户可以从“已归档”中恢复对话；恢复会产生一次状态变更记录。
- 归档是逻辑状态变更，不删除 Provider 侧会话文件。后端连接按正常空闲回收策略释放。

## 状态

对话状态使用以下集合：

| 状态 | 含义 | 可发送消息 | 可恢复 |
| --- | --- | ---: | ---: |
| `current` | 当前草稿选中的对话 | 是 | — |
| `idle` | 可继续的历史对话 | 否，先切换 | 是 |
| `archived` | 用户主动归档 | 否 | 是 |
| `needs_rebuild` | 后端上下文不可安全恢复 | 否 | 通过重建 |
| `deleted` | 已随草稿清理 | 否 | 否 |

轮次状态仍沿用现有 `queued`、`running`、`cancel_requested`、`completed`、`failed`、`interrupted`。轮次状态不能替代对话状态；例如对话可以是 `current`，但当前没有活动轮次。

## API 约定

API 以草稿为边界，所有写操作都需要幂等请求 ID 和草稿修订号。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/drafts/:draftId/conversations` | 查询当前、历史和已归档对话 |
| `POST` | `/api/drafts/:draftId/conversations` | 创建新对话 |
| `POST` | `/api/drafts/:draftId/conversations/:id/resume` | 切换并继续指定对话 |
| `POST` | `/api/drafts/:draftId/conversations/:id/rebuild` | 创建重建上下文 |
| `POST` | `/api/drafts/:draftId/conversations/:id/archive` | 归档对话 |
| `POST` | `/api/drafts/:draftId/conversations/:id/restore` | 恢复已归档对话 |
| `GET` | `/api/drafts/:draftId/messages?conversationId=:id` | 查询指定对话消息 |

服务端约束：

- `conversationId` 不属于该草稿时返回 `404`，不能泄露其他草稿是否存在。
- 已归档或需要重建的对话直接提交创作轮次时返回 `409 CONVERSATION_CONFLICT` 或 `409 SESSION_REBUILD_REQUIRED`。
- 同一 `requestId` 重复请求返回第一次受理结果；相同请求 ID 携带不同请求体时返回 `409 REQUEST_CONFLICT`。
- 未传 `conversationId` 的旧客户端请求继续解析草稿当前对话，不得隐式创建多个对话。
- 消息查询默认按草稿过滤；新 UI 显式传入对话 ID，旧消息未关联对话时归入“旧版历史”。

## 页面验收

- 打开草稿后，当前对话及其消息可以正确恢复；刷新不会创建新对话。
- 点击“新对话”后，旧消息仍可在历史对话中查看，新对话不会引用旧上下文。
- 切换到历史对话后，消息列表、Provider、模型和状态展示一致，发送消息只写入所选对话。
- 归档后对话从当前列表移出，消息仍可查询；恢复后可以继续发送。
- 服务重启后，可恢复会话显示为可继续；无法安全恢复的会话显示“需要重建”，且不会自动重发上一轮。
- 切换工作流或草稿后，列表和消息立即隔离；不能通过旧页面继续提交到已切换的草稿。
- 有活动轮次时，新对话、切换对话、归档、删除草稿均被正确阻止，并显示可理解的原因。
- 已发布工作流的运行详情不出现创作对话消息；同一工作流的不同运行之间不共享创作上下文。

## 非目标

- 第一版不支持多个用户共享或协作编辑同一对话。
- 第一版不支持把一段对话迁移到另一个工作流或草稿。
- 第一版不支持将已归档对话直接合并到当前对话。
- 第一版不自动使用模型生成标题或摘要；标题和历史摘录使用确定性规则。
- 第一版不提供对话消息的单条删除或编辑，避免破坏轮次和后端上下文的一致性。

## 实施边界

本 feature 依赖现有 Agent 会话设计中的 `agent_conversations`、轮次和消息关联能力。若需要新增或调整数据库表、字段、索引或外键，必须先完成数据库结构审核，审核通过后再执行迁移；产品交互和 API 文档可以先行更新。

实现应同步更新：

- `docs/wiki/interface.md`：补充对话选择器、新对话、继续对话和归档的页面说明。
- `docs/features/agent-conversations/implementation-status.md`：记录历史筛选、归档恢复和真实环境验收进度。
- 对应 API、Store、服务层和 UI 的契约测试。

## 开发指导

本节是交给实现 Agent 的执行规格。实现 Agent 应优先复用
`docs/features/agent-conversations/design.md` 中已有的会话、轮次、幂等和恢复契约；本 feature 只补充历史管理和工作流绑定行为。若本节与底层设计冲突，以底层设计中“实现约束”章节为准，并在提交说明中指出冲突。

### 推荐实现顺序

1. **领域类型与状态转换**：集中定义 `ConversationStatus`、`ConversationView`、归档/恢复命令 DTO 和状态转换函数。
2. **Store 查询与原子命令**：增加按 `draftId` 查询、创建、切换、归档、恢复、重建的事务方法；写操作统一校验草稿修订号和对话归属。
3. **服务层编排**：由 `src/authoring/conversations.ts`（或同职责模块）处理活动轮次检查、草稿保存前置条件、Provider / model 快照和后端上下文轮换。
4. **API 接入**：实现列表、创建、继续、重建、归档、恢复接口；路由层只做参数解析、错误映射和序列化。
5. **前端状态与交互**：在 `DraftPage` 中分离对话列表、选中对话、活动轮次和连接状态；SSE 事件校验 `draftId`、`conversationId`、`turnId`。
6. **验收与文档**：先跑模拟 Provider 契约测试，再做浏览器和真实 Provider 验收，并同步 `implementation-status.md`。

### 建议数据契约

```ts
type ConversationView = {
  id: string;
  draftId: string;
  title: string | null;
  status: "current" | "idle" | "archived" | "needs_rebuild";
  mode: "single" | "multi";
  providerId: string;
  modelId: string;
  contextMode: "native" | "legacy";
  createdAt: string;
  updatedAt: string;
  archivedAt: string | null;
  lastUserMessage: string | null;
  lastTurnStatus: string | null;
  connectionState: "disconnected" | "connecting" | "ready" | "needs_rebuild";
  activeTurnId: string | null;
};
```

命令请求至少包含 `requestId` 和 `expectedDraftRevision`。需要指定对话的命令额外包含 `conversationId`；重建命令额外包含 `rebuildFromId`。服务端不得接受前端直接传入后端 session 文件路径、原生 thread ID 或连接代次。

### 状态转换与事务边界

| 当前状态 | 操作 | 结果 | 条件 |
| --- | --- | --- | --- |
| 无对话 | 创建 | `current` | 草稿存在 |
| `current` | 新对话 | 旧为 `idle`，新为 `current` | 无活动轮次 |
| `idle` | 继续 | 旧 `current` 为 `idle`，目标为 `current` | 目标属于同一草稿 |
| `archived` | 恢复 | `current` | 无活动轮次 |
| `needs_rebuild` | 重建 | 原会话保留，新会话 `current` | 新后端上下文创建成功 |
| `current` / `idle` | 归档 | `archived` | 无活动轮次 |

新对话应在一个事务内完成：校验草稿修订号 → 检查活动轮次 → 将旧当前对话改为 `idle` → 插入新对话及配置快照 → 写入幂等回执和状态事件。事务提交后再创建后端连接；连接失败时将新会话标记为 `needs_rebuild`，不能偷偷切回旧对话。

以下操作必须拒绝且保持数据库不变：跨草稿操作、归档有活动轮次的会话、活动轮次期间新建或切换、对已归档会话直接提交消息、把不同 Provider / model 的快照写回旧会话。

### 继续、重建与重试

- **继续**复用同一个逻辑对话；后端引用可验证时恢复原生上下文，不重复发送上一轮 prompt。
- **重建**创建新的后端上下文，可带确定性历史摘录，但必须显示“新上下文”并记录 `rebuildFromId`。
- **重试**只允许重试尚未提交给 Provider 的受理失败。已受理但终态未知的轮次必须进入 `interrupted` 或使会话进入 `needs_rebuild`，禁止自动重发。

### API 和错误处理

API 以草稿为边界：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/drafts/:draftId/conversations` | 查询对话列表 |
| `POST` | `/api/drafts/:draftId/conversations` | 创建新对话 |
| `POST` | `/api/drafts/:draftId/conversations/:id/resume` | 切换并继续 |
| `POST` | `/api/drafts/:draftId/conversations/:id/rebuild` | 重建上下文 |
| `POST` | `/api/drafts/:draftId/conversations/:id/archive` | 归档 |
| `POST` | `/api/drafts/:draftId/conversations/:id/restore` | 恢复归档 |
| `GET` | `/api/drafts/:draftId/messages?conversationId=:id` | 查询消息 |

错误统一使用稳定 `AppError.code`：跨草稿或不存在返回 `404`；修订冲突、状态冲突和活动轮次返回 `409`；需要重建返回 `SESSION_REBUILD_REQUIRED`；Provider 不可用返回 `503`。前端不得根据错误文本判断分支。

### 前端实现要点

- 对话列表使用服务端 `updatedAt` 排序，选中对话后消息请求必须显式携带 `conversationId`。
- 切换草稿时取消旧 SSE 订阅，并丢弃旧 `draftId` 的迟到事件。
- 当前对话有活动轮次时，禁用新建、切换、归档、恢复、发布、测试和删除。
- `needs_rebuild` 显示原因和重建入口，不显示为普通连接失败。
- 归档确认需说明消息保留、对话停止接收新消息。

### 测试矩阵

**Store / 服务层**

- 首次创建只有一个 `current`；重复 `requestId` 不产生重复记录。
- 并发新建只有一个成功，另一个收到冲突。
- 切换、归档、恢复、重建符合状态表。
- 跨草稿 ID 返回 `404`，不读取对方消息。
- 活动轮次期间所有会话管理命令均被拒绝。
- 服务重启不会自动重发终态未知的 prompt。

**API / 前端**

- 列表只返回指定草稿；显式和兼容路径均指向正确会话。
- 新对话不显示旧消息，历史入口仍可查看旧消息。
- 切换草稿后迟到 SSE 不污染当前页面。
- 错误按 `code` 显示对应操作，不依赖错误文本。

**真实环境**

- 一个原生 Provider 完成三轮连续创作和服务重启恢复。
- 新对话与旧对话的后端上下文隔离。
- 归档并恢复后消息完整，Provider / model 快照未被覆盖。

### 完成定义

只有 API、Store、服务层和 UI 都支持新对话、继续、归档和恢复，且幂等、并发冲突、活动轮次阻止、重启恢复、草稿隔离均有自动化测试，并完成至少一次真实 Provider 的连续多轮和上下文隔离验收，才可将 feature 标记为完成。
